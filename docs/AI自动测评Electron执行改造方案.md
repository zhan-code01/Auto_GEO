# AI 自动测评 Electron 执行改造方案

> 当前实施说明（2026-07-09）：开发测试环境默认使用 Headed，打包交付默认使用
> Headless，也可通过 `GEO_EVALUATION_DEFAULT_BROWSER_MODE=headed|headless` 显式覆盖。
> 两种环境触发风控时都会关闭原浏览器并重新创建 Headed 浏览器；处理完成后恢复各自默认模式。
> 所有中断任务都释放平台名额，只能由用户点击“继续执行”恢复，也可以主动取消。
>
> 执行架构已统一为：Electron只负责轮询、领取任务和管理子进程；
> `backend/workers/geo_evaluation_worker.py`由Electron在用户电脑启动，
> 实际Playwright操作统一复用Python平台适配器。旧Electron TypeScript平台适配器已经停用。
> 每个任务固定绑定一个`account_id`，人工重新登录后同时更新该账户、用户安全会话和本地缓存。

> 本文是后续代码实施的依据，用于固定已经确认的业务目标、执行流程、时间规则、异常处理和验收标准，避免开发过程中出现理解偏差。

## 1. 背景

AutoGeo 会先为客户生成并冻结一套测评问题集，默认包含 100 个问题。用户选择一个 AI 测评平台后，可以执行：

- 建立使用前基线；
- 执行使用后复测。

系统需要使用冻结的问题集逐题询问所选 AI 平台，收集真实回答，再由后端计算该平台的四项指标：

- AI 可见度；
- 出现覆盖率；
- 推荐排名；
- 情感分。

当前 Electron 中的 AI 问询与回答提取逻辑过于简单，长时间执行 100 题时，在回答完整性、风控识别、人工接管、断点恢复和结果可靠性方面都不够稳定。

同时，浏览器必须运行在用户本机，而不是由服务器端浏览器代替。用户需要能够在登录过期、验证码、滑块或安全验证出现时，直接在本机可见浏览器中完成人工处理。

## 2. 改造目标

本次改造的最终目标是：

1. 后端负责任务创建、状态管理、原始回答保存、四项指标计算和结果展示。
2. Electron 负责领取任务，使用用户本机 Chrome 和本地登录状态操作 AI 平台。
3. 每个任务只对应一个测评平台和一套冻结的 100 题问题集。
4. 每道题使用全新的页面和全新的 AI 对话，避免上下文污染。
5. 默认使用 Headless 浏览器自动执行。
6. 进入平台后进行第一次登录/风控检测。
7. 发送问题后进行第二次风控检测，并在等待回答期间持续监测。
8. 发现登录过期或人工验证后，关闭 Headless，启动 Headed 浏览器并永久等待用户处理。
9. 人工处理完成后，使用 Headed 重新执行当前题；成功后，剩余问题恢复 Headless。
10. 回答获取以平台“复制”按钮为主，DOM 提取为兜底。
11. 每题完成并经后端确认保存后，随机等待 10～15 秒再执行下一题。
12. 支持不同平台任务并行、平台内部严格串行。
13. 支持本地持久化、断点续跑、上传重传和幂等保存。

## 3. 不在本次改造范围内的事项

- 不改变四项指标的业务定义。
- 不将多个平台的指标合并成综合指标。
- 不允许一条任务同时包含多个测评平台。
- 不尝试自动破解或绕过验证码、滑块、安全验证。
- 不立即删除后端旧 Playwright 代码；先让 Electron 新链路稳定，再逐步停止重复执行入口。
- 不使用固定等待时间代替回答完成判断。

## 4. 核心职责划分

### 4.1 后端职责

后端负责：

- 管理问题集和问题集版本；
- 创建使用前基线或使用后复测任务；
- 保证同一平台同一时间只有一个活动任务；
- 向 Electron 提供任务和完整问题列表；
- 记录任务状态、平台状态、当前题目和心跳；
- 接收并幂等保存每道题的原始回答；
- 异步计算每道回答对应的四项指标；
- 汇总当前平台的测评结果；
- 管理人工介入、中断、继续、取消和完成状态；
- 判断 Electron 是否失联。

后端不负责本地测评任务的浏览器操作。

### 4.2 Electron 职责

Electron 负责：

- 轮询后端待执行任务；
- 领取任务并发送心跳；
- 查找并启动用户本机 Chrome；
- 加载平台本地登录状态；
- 按题目顺序操作 AI 平台；
- 创建新页面和新对话；
- 执行两阶段风控检测；
- 发送问题并确认发送成功；
- 等待回答完整生成；
- 通过复制按钮或 DOM 获取回答；
- 校验回答有效性；
- 保存本地执行检查点；
- 将回答可靠上传至后端；
- 在登录过期或风控时切换到 Headed；
- 在客户端恢复后继续未完成任务。

## 5. 任务模型

### 5.1 单任务单平台

用户在页面下拉框中选择一个平台，然后点击“建立使用前基线”或“执行使用后复测”。

例如：

```text
选择豆包
→ 点击建立使用前基线
→ 后端创建“豆包 + 当前冻结问题集 + 100题”的任务
→ 最终只生成豆包的四项指标
```

同理，选择千问或 DeepSeek 时，创建的是另一条独立任务。

### 5.2 并行规则

- 同一个平台同一时间只能运行一条任务。
- 不同平台最多允许三条任务同时运行。
- 豆包、千问、DeepSeek 各自拥有独立的浏览器、登录上下文、进度、等待时间和风控状态。
- 一个平台注册人工验证时，另外两个平台继续执行。

示例：

```text
豆包任务      → DoubaoWorker      → 独立浏览器
千问任务      → QianwenWorker     → 独立浏览器
DeepSeek任务  → DeepSeekWorker    → 独立浏览器
```

### 5.3 平台内部串行

同一平台的 100 道题严格串行执行，不允许并发提问：

```text
第1题完成并上传
→ 等待10～15秒
→ 第2题
→ 等待10～15秒
→ ...
→ 第100题
```

## 6. 问题集与前后测规则

### 6.1 问题集冻结

- 测评前先生成默认 100 题的问题集。
- 建立基线和使用后复测必须引用同一个冻结的问题集版本。
- Electron 不生成或改写问题，只执行后端下发的问题。

### 6.2 重新生成问题集

重新生成问题集时：

- 创建新的问题集版本；
- 原问题集和原基线作为历史记录保留；
- 新问题集不能直接与旧问题集基线比较；
- 新问题集必须重新建立使用前基线。

### 6.3 多次使用后复测

- 同一基线允许执行多次使用后复测；
- 每次复测生成独立记录；
- 每次复测都与相同问题集版本的基线比较；
- 历史复测记录用于趋势展示。

### 6.4 有效样本

允许部分题目最终失败。

- 绝对指标使用当次成功回答计算；
- 页面明确显示有效样本数，例如 `96/100`；
- 使用前后变化只使用两次都成功的相同问题交集；
- 例如使用前成功 96 题、使用后成功 98 题、共同成功 94 题，则变化指标使用这 94 题计算。

## 7. Electron 模块设计

现有 `geo-evaluation-engine.ts` 不再继续堆积全部职责，建议拆分为以下模块。

### 7.1 任务轮询与协调

建议模块：

```text
GeoEvaluationCoordinator
GeoEvaluationTaskPoller
```

职责：

- 轮询任务；
- 限制最多三个不同平台任务并行；
- 限制同平台只运行一个任务；
- 启动和停止平台 Worker；
- 汇总状态并通知渲染进程。

### 7.2 平台 Worker

建议模块：

```text
PlatformEvaluationWorker
```

职责：

- 执行某一平台的一条任务；
- 维护当前问题和重试次数；
- 执行题目间隔；
- 管理连续失败计数；
- 保存执行检查点；
- 处理暂停、继续和取消。

### 7.3 浏览器会话管理

建议模块：

```text
EvaluationBrowserSession
```

职责：

- 启动 Headless 或 Headed Chrome；
- 创建并保存 BrowserContext；
- 加载和更新本地 storage state；
- 每题创建新页面；
- 人工介入时切换浏览器模式；
- 关闭异常页面和浏览器。

### 7.4 平台适配器

建议接口：

```text
AiPlatformAdapter
├── DoubaoAdapter
├── QianwenAdapter
└── DeepSeekAdapter
```

每个平台适配器负责：

- 平台新对话入口；
- 输入框定位；
- 发送按钮定位；
- 发送成功判断；
- 生成中状态判断；
- 最新 AI 回答容器定位；
- 复制按钮定位；
- DOM 回答提取；
- 平台特有弹窗处理。

后端现有平台 Checker 中成熟的选择器、回答清理和质量校验规则应迁移为 TypeScript 实现。Codegen 生成的选择器作为候选和兜底，不能将动态 CSS 类名作为唯一依据。

### 7.5 风控检测

建议模块：

```text
EvaluationRiskDetector
```

职责：

- 登录失效检测；
- 登录弹窗和二维码检测；
- 验证码、滑块和 iframe 检测；
- 安全验证、访问异常和操作频繁检测；
- HTTP 401、403、429 等异常响应检测；
- 正常聊天页面正向信号检查；
- 输出结构化风险类型和用户提示。

### 7.6 回答采集

建议模块：

```text
EvaluationAnswerCapture
```

职责：

- 判断回答是否完整生成；
- 暂存并恢复用户剪贴板；
- 点击最后一条回答的复制按钮；
- 读取和校验复制结果；
- 复制失败时调用平台 DOM 兜底；
- 防止抓到旧回答、用户问题或页面菜单。

### 7.7 本地检查点与上传队列

建议模块：

```text
EvaluationCheckpointStore
EvaluationResultUploader
```

职责：

- 本地持久化当前题执行状态；
- 保存已抓取但未确认上传的回答；
- 网络恢复后重传；
- 后端确认前阻止该平台执行下一题；
- 支持 Electron 重启后的自动恢复。

## 8. 浏览器与页面生命周期

### 8.1 浏览器粒度

每个平台任务保持：

- 一个浏览器实例；
- 一个登录 BrowserContext；
- 每题一个全新 Page。

不为每题重新启动整个 Chrome，避免 100 次浏览器启动开销和额外故障。

### 8.2 每题页面隔离

每道题结束后关闭当前页面，下一题创建全新页面并进入平台新对话入口：

```text
保持Browser
→ 保持BrowserContext
→ 创建Page A执行第1题
→ 关闭Page A
→ 等待10～15秒
→ 创建Page B执行第2题
```

新页面不能进入上一题的会话 URL，必须进入平台新对话入口。

### 8.3 登录状态保存

- BrowserContext 使用本地保存的 storage state。
- 每题完成后可以更新本地 storage state。
- 人工登录或验证完成后必须立即保存新状态。
- 登录状态只保存在用户本机；后端只保存必要的账号绑定元信息。

## 9. 单题自动执行状态机

单题正常流程固定如下：

```text
创建全新页面
→ 进入平台新对话入口
→ 第一次登录/风控检测
→ 定位输入框
→ 输入问题
→ 点击发送
→ 确认问题发送成功
→ 第二次风控检测，并在等待回答期间持续监测
→ 判断回答生成完成
→ 点击最后一条AI回答的复制按钮
→ 读取并校验剪贴板
→ 复制失败则提取最后一条AI回答DOM
→ 本地保存回答和上传状态
→ 上传后端
→ 等待后端确认保存
→ 关闭页面
→ 随机等待10～15秒
→ 执行下一题
```

### 9.1 输入问题

- 必须定位可见且可编辑的输入框；
- 输入前清空输入框；
- 输入后读取输入框内容，确认和目标问题一致；
- 优先使用平台稳定的可访问性属性、placeholder、test id；
- 输入失败时不得直接点击发送。

### 9.2 确认发送成功

点击发送按钮后，同时观察：

- 输入框是否清空；
- 聊天区是否出现当前问题；
- 是否出现新的用户消息节点；
- AI 是否进入生成或思考状态。

至少必须确认当前问题已经出现在聊天区，才进入回答等待阶段。

## 10. 两阶段风控检测

风控检测只设置在两个业务位置，避免重复且混乱的检查点。

### 10.1 第一次：进入平台后

时机：

```text
进入新对话页面
→ 页面基本加载完成
→ 输入问题之前
```

负责检测：

- 登录状态过期；
- 跳转登录页；
- 登录二维码或登录弹窗；
- 页面初始化时出现的验证码；
- 账号异常、安全验证；
- 聊天输入框不可用。

### 10.2 第二次：发送问题后

时机：

```text
问题发送成功
→ 等待回答生成期间
```

第二次检测不是只执行一次，而是在回答等待循环中持续执行，直到：

- 回答生成完成；或
- 检测到风控；或
- 普通回答等待超时。

负责检测：

- 发送问题触发的验证码或滑块；
- 操作频繁；
- 异常访问；
- 安全验证；
- 登录状态突然失效；
- HTTP 401、403、429；
- 聊天页面被验证页面替换或遮挡。

### 10.3 风控识别依据

检测器综合使用：

- URL 特征：`login`、`passport`、`captcha`、`verify` 等；
- 可见文字：请登录、安全验证、操作频繁、异常访问等；
- 可见控件：密码框、二维码、验证码、滑块；
- iframe 和遮罩层；
- 网络响应状态码；
- 正常聊天输入框和聊天区域是否存在。

不能只因为导航栏出现“登录”文字就判定风控，必须结合可见性和正常页面正向信号，减少误判。

## 11. 回答完成判断

不使用固定等待时间。

回答完成需要综合满足：

1. “停止生成”“思考中”“生成中”等状态消失；
2. 最后一条 AI 回答的复制按钮出现并可用；
3. 回答内容连续 2～3 秒保持稳定。

建议每 1 秒读取一次最新回答状态，连续 3 次没有变化时视为稳定。

如果平台存在明确的完成信号，例如“重新生成”“复制”工具栏出现，可作为加强信号。

## 12. 回答获取策略

### 12.1 第一优先级：复制按钮

三个平台分别实现复制逻辑：

- 豆包：在最后一条 AI 回答容器内点击“复制”；
- 千问：在最后一条 AI 回答容器内点击“复制为 Markdown”；
- DeepSeek：在最后一条 AI 回答容器内点击“复制”。

必须先定位最后一条 AI 回答容器，再在容器内部找复制按钮，不能点击整页第一个复制按钮。

### 12.2 剪贴板保护

复制流程：

```text
暂存用户原剪贴板
→ 清空剪贴板或写入内部哨兵值
→ 点击当前AI回答的复制按钮
→ 等待剪贴板变化
→ 读取回答
→ 校验回答
→ 恢复用户原剪贴板
```

浏览器上下文需要具备必要的剪贴板读写权限。

无论成功、失败还是发生异常，都必须在 `finally` 中尝试恢复用户剪贴板。

### 12.3 第二优先级：DOM 提取

复制失败时，只从最后一条新增 AI 回答容器中提取 DOM：

- 优先提取 Markdown 正文；
- 排除复制、分享、点赞、重新生成等工具栏；
- 排除用户问题；
- 排除推荐问题列表；
- 排除侧边栏和历史对话；
- 不读取整个页面 `body` 作为正式答案。

### 12.4 回答有效性校验

上传前至少检查：

- 内容不为空；
- 不是当前问题原文；
- 不是发送前已有的旧回答；
- 不是登录、验证码或错误提示；
- 不是页面菜单或推荐问题；
- 达到合理的最小长度；
- 来源是发送当前问题后新增的最后一条 AI 回答。

## 13. Headless 与 Headed 人工接管

### 13.1 默认模式

所有自动测评默认使用 Headless。

### 13.2 触发条件

以下情况直接进入人工接管，不消耗普通重试次数：

- 登录状态过期；
- 登录二维码；
- 验证码；
- 滑块；
- 人机验证；
- 安全验证；
- 操作频繁；
- 账号或访问异常；
- 页面明确要求人工确认。

### 13.3 接管流程

```text
Headless检测到登录或风控
→ 停止当前题
→ Electron上报manual_required
→ 后端暂停该平台普通任务超时
→ 保存当前题检查点
→ 关闭该平台Headless浏览器
→ 使用相同本地登录状态启动Headed浏览器
→ 打开对应平台
→ 永久等待用户处理
```

### 13.4 人工处理完成判断

不能只根据验证文字消失判断完成，必须确认：

- 登录页或验证层消失；
- 页面不再要求登录；
- 正常聊天区域存在；
- 输入框存在、可见并可输入。

### 13.5 当前题恢复

人工处理完成后：

1. 保存新的本地登录状态；
2. 在 Headed 中创建新对话；
3. 重新发送当前问题；
4. 获取并上传当前题回答；
5. 关闭 Headed 浏览器；
6. 剩余问题重新使用 Headless。

即使风控是在原问题发送后出现，也重新发送当前题，因为原回答可能没有生成或不完整。

### 13.6 多平台同时人工介入

- 允许同时打开多个 Headed 窗口；
- 每个窗口明确标注平台名称和当前任务；
- 用户分别处理；
- 一个平台注册人工验证不暂停其他平台。

## 14. 时间与超时规则

默认时间配置如下：

| 项目 | 默认值 | 说明 |
|---|---:|---|
| Electron 轮询任务 | 15 秒 | 空闲时查询待领取任务 |
| 任务心跳 | 30 秒 | `running`、`manual_required` 均持续发送 |
| 后端失联判断 | 120 秒 | 超过此时间无心跳视为客户端中断 |
| 页面加载超时 | 60 秒 | 单次页面导航 |
| 输入框等待 | 20 秒 | 等待可用输入区域 |
| 回答开始等待 | 30 秒 | 等待 AI 开始生成 |
| 完整回答等待 | 120 秒 | 等待回答稳定完成 |
| 单题普通执行上限 | 180 秒 | 不包含人工处理时间 |
| 正常题目间隔 | 随机 10～15 秒 | 后端确认保存后开始计算 |
| 普通失败重试间隔 | 随机 10～15 秒 | 当前题重试 |
| 单题最大普通尝试 | 3 次 | 人工验证不计入 |
| 人工处理等待 | 永久 | Electron 在线且持续心跳时不超时 |

时间配置应由后端任务配置统一下发或由共享配置维护，避免前后端出现两套互相冲突的数值。

## 15. 普通失败与熔断

### 15.1 单题普通失败

以下属于普通失败：

- 网络临时错误；
- 页面加载失败；
- 输入或发送失败；
- 回答等待超时；
- 复制失败且 DOM 兜底失败；
- 回答质量校验失败。

处理规则：

```text
当前题失败
→ 等待10～15秒
→ 重新创建全新页面
→ 重试当前题
→ 最多尝试3次
```

3 次仍失败：

- 记录当前题失败和明确原因；
- 关闭当前页面；
- 等待正常题目间隔；
- 继续下一题。

### 15.2 连续失败熔断

如果连续 3 道题最终失败：

1. 重启一次该平台 Headless 浏览器；
2. 重新加载本地登录状态；
3. 再执行当前待处理题；
4. 重启后再失败 1 题，则暂停该平台；
5. 后端标记为“执行中断，可继续”。

其他平台继续执行。

### 15.3 恢复规则

- 断网、Electron 退出、电脑重启造成的中断：客户端重新上线后自动续跑；
- 连续失败熔断造成的中断：用户点击“继续执行”后续跑；
- 已经被后端确认保存的题目不重复询问；
- 未完成或未确认保存的当前题重新处理。

## 16. 本地持久化与可靠上传

### 16.1 检查点

Electron 至少保存：

- run id；
- platform；
- prompt id；
- round no；
- question；
- 当前执行阶段；
- 普通尝试次数；
- 回答内容；
- 回答采集方式；
- 上传状态；
- 后端确认状态；
- 最后更新时间。

### 16.2 上传失败

回答已经抓取成功但上传失败时：

```text
回答持久化到本地
→ 暂停该平台下一题
→ 持续重传
→ 后端确认幂等保存
→ 开始10～15秒等待
→ 继续下一题
```

不能因为上传失败丢弃已经获得的有效回答，也不能在未确认保存时继续大量提问。

### 16.3 幂等键

建议使用以下组合标识单条回答：

```text
run_id + platform + round_no + prompt_id
```

后端重复收到同一结果时更新或返回已有结果，不产生重复记录。

## 17. 后端接收与异步指标计算

Electron 上传原始回答后：

```text
后端校验任务归属和幂等键
→ 保存原始回答
→ 更新回答采集进度
→ 立即向Electron确认已保存
→ 将四项指标计算放入后台任务
→ 更新指标计算进度
```

Electron 不等待四项指标计算完成，只等待原始回答已经可靠保存。

界面可以分别展示：

- 回答采集进度，例如 `67/100`；
- 指标计算进度，例如 `61/100`。

## 18. 任务状态

建议统一状态：

| 状态 | 含义 |
|---|---|
| `pending` | 等待 Electron 领取 |
| `running` | 正在自动执行 |
| `manual_required` | 等待用户登录或完成验证 |
| `interrupted` | 客户端失联或连续失败熔断，可继续 |
| `completed` | 所有问题处理完成，允许包含少量失败题 |
| `failed` | 任务级不可恢复错误 |
| `cancelled` | 用户主动取消 |

平台任务在人工处理时保持 `manual_required`，不被普通任务超时判定为失败。

## 19. 前后端通信

后端至少需要支持：

- 轮询待执行任务；
- 领取任务；
- 获取完整任务 payload；
- 发送心跳；
- 上报当前进度；
- 上报人工介入；
- 上报人工处理完成；
- 幂等提交单题原始回答；
- 上报单题最终失败；
- 标记任务完成；
- 标记任务中断；
- 自动恢复或用户确认继续；
- 取消任务。

人工介入事件至少包含：

```json
{
  "run_id": 1001,
  "platform": "doubao",
  "prompt_id": 67,
  "stage": "before_input",
  "risk_type": "login_required",
  "message": "豆包登录状态已过期，需要用户重新登录"
}
```

单题结果至少包含：

```json
{
  "run_id": 1001,
  "platform": "doubao",
  "prompt_id": 67,
  "round_no": 1,
  "question": "问题内容",
  "success": true,
  "answer": "完整原始回答",
  "capture_method": "clipboard",
  "attempt_count": 1
}
```

## 21. 测试重点

### 21.1 正常路径

- 三个平台分别能完成单题；
- 复制结果准确；
- DOM 兜底准确；
- 每题使用新页面和新对话；
- 10～15 秒间隔生效；
- 原始回答成功上传；
- 四项指标异步计算；
- 单平台 100 题可完成。

### 21.2 并行路径

- 三个不同平台任务可以同时执行；
- 同平台第二条任务被拒绝；
- 三个平台登录状态、进度、剪贴板和浏览器互不串扰；
- 一个平台注册人工时其他平台继续。

### 21.3 风控路径

- 启动时登录过期；
- 输入前出现登录弹窗；
- 发送后出现验证码；
- 等待回答时出现滑块；
- 401、403、429 响应；
- Headed 永久等待；
- 人工处理完成后重做当前题；
- 后续恢复 Headless。

### 21.4 失败恢复

- 单题失败重试 3 次；
- 连续 3 题失败后重启浏览器；
- 重启后再失败则中断；
- 上传失败时本地保存并重传；
- Electron 重启后自动续跑；
- 熔断中断需要用户点击继续；
- 幂等提交不产生重复记录。

## 22. 验收标准

满足以下条件后，本次改造才视为完成：

1. 浏览器操作全部发生在 Electron 客户端本机。
2. 单次任务只测一个平台，最多三个不同平台任务并行。
3. 同平台同一时间只有一条活动任务。
4. 100 道题逐题串行，每题使用全新页面和全新对话。
5. 每题之间随机等待 10～15 秒。
6. 回答获取以复制按钮为主、DOM 为兜底。
7. 回答完整性通过生成状态、复制按钮和 2～3 秒稳定性综合判断。
8. 风控仅在进入平台后和发送问题后两个业务阶段检测，发送后持续检测至回答完成。
9. 登录过期和验证码均能自动切换到 Headed。
10. 人工处理默认永久等待，且其他平台不受影响。
11. 人工处理成功后重新执行当前题，剩余题恢复 Headless。
12. 回答上传失败不会丢失，也不会继续执行下一题。
13. 意外中断可以自动续跑，连续失败中断可以手动继续。
14. 后端先确认保存原始回答，再异步计算四项指标。
15. 使用前后变化只使用共同成功问题计算，并展示有效样本数。
16. 真实平台 100 题稳定性测试通过。

## 23. 已确认决策汇总

- 每题使用新对话：是。
- 每题关闭页面并创建新页面：是。
- 每题关闭整个浏览器：否。
- 默认浏览器模式：Headless。
- 风控后模式：Headed。
- 人工完成后剩余题恢复 Headless：是。
- 登录过期按人工验证处理：是。
- 人工等待超时：无，永久等待。
- Electron 失联：标记“执行中断，可继续”。
- 正常题目间隔：随机 10～15 秒。
- 三个平台任务并行：允许。
- 一个平台注册人工时其他平台继续：是。
- 多个人工窗口同时打开：允许。
- 同平台多任务并行：不允许。
- 单题普通尝试：最多 3 次。
- 连续 3 题失败：重启一次浏览器。
- 重启后再失败：中断该平台，用户手动继续。
- 意外退出或断网：自动续跑。
- 回答提取：复制按钮优先，DOM 兜底。
- 回答完成：生成状态消失、复制按钮出现、内容稳定 2～3 秒。
- 剪贴板：暂存并恢复。
- 上传失败：本地保存、暂停平台、持续重传。
- 后端指标计算：保存回答后异步计算。
- 部分成功：允许生成指标并显示有效样本数。
- 前后比较：只比较共同成功问题。
- 多平台指标汇总：不需要，指标只描述当前所选平台。
