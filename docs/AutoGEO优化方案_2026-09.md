# AutoGEO 优化方案(2026-09)

> 依据:2026-09 竞品现状调研(六大差距)与代码现状核查(2026-09-06)  
> 代码基线:`Auto_GEO-main-master`(2026-08-21 对应版本)  
> 方案原则:每项包含 **现状与差距 → 优化目标(量化) → 解决方案(落实到具体文件) → 验收标准 → 工作量**

---


## 〇、总体目标

**定位升级**:从"自媒体批量发布的 GEO 自动化工具",升级为"**合规可信、效果可验证的品牌 AI 可见度管理平台**"。国内第一梯队(泓动"全栈引擎+效果对赌"、迈富时"T-GEO 认知工程")已具备的能力,本方案予以补齐;国际产品(Profound)"监测后由 Agent 自动执行"的思路予以借鉴,落地为优化项五;国际平台监测列入 2027 年规划。

**总目标拆解为 6 项,量化指标(2026 年第四季度前)**:

| # | 优化项       | 核心量化目标                                    | 优先级    | 预估工作量                    | 主责角色     |
| - | --------- | ----------------------------------------- | ------ | ------------------------ | -------- |
| 1 | 测评平台广度    | 覆盖 **3 → 5**(首批元宝/文心)→ **7**(二批 Kimi/夸克;夸克 Web 探针不可用时秘塔顶替)  | **P0** | 首批 1.5～2 周;二批另加 1～1.5 周  | 后端+客户端   |
| 2 | 合规与白帽体系   | 全链路审计可溯源;发布重复率≤阈值;输出方法论白皮书                | **P0** | 1～2 周(工程)                | 后端+商务/法务 |
| 3 | 权威信源接入    | 新闻稿分发上线,权威信源在 cited_domains 占比较基线提升 ≥15pp | P1     | 1～2 周                    | 后端+商务    |
| 4 | 效果可验证     | 优化前→优化后自动对比报告(含测量方差控制);支持按效果交付口径          | P1     | 1～1.5 周(聚合侧为主,账号防污染逻辑另计) | 后端+前端    |
| 5 | Agent 行动层 | Agent 可基于测评短板给出并执行优化动作(带人工确认)             | P2     | 2 周                      | 后端(AI)   |
| 6 | 竞品与来源分析   | 引用证据链修复(前置)+ 项目级聚合 + 报表接入                 | P0→P2  | 证据链 1～2 周 + 聚合 3 人日      | 后端+前端    |

> **主线顺序**:代码静态核对发现,引用证据链尚未建立(测评 Worker 提交结果时 `citations` 固定为 `[]`),来源分析、SOV、权威信源效果等指标虽可计算、但缺乏可信度。因此执行主线为:先修复证据链与指标可信度,再扩展平台,最后开展效果承诺与 Agent 执行。

> **排期建议(闸门式)**:  
> **第 0 周:冻结口径**:问题集、判卷 prompt 版本、指标定义、数据契约(含 `measurement_type` 与 `phase` 的映射)、平台能力矩阵、基线采样协议、算法契约默认值(simhash 归一化与标题相似阈值)、引用状态判定映射表、平台门槛数值、回滚观察窗口、统计默认值(最小可检测效应/置信区间/样本下限)全部冻结,作为后续一切对比的同口径基准;并行启动新平台账号申请与实名/授权(元宝/文心/Kimi/夸克,账号注册与培育存在前置周期,商务+客户端并行),并完成四平台 Web 端可用性探针(页面结构、引用展示、登录态稳定性)。  
> **第 1～3 周:修复引用证据链(P0)**:测评 Worker 不再丢弃引用(`citations` 真实落库)、`null/[]/unavailable` 状态区分、原始证据保存、回答-引用关联、幂等与脱敏;并行开展审计数据表建设(项二)与竞品份额口径重写(项六)。  
> **第 4～5 周:指标可信度(P0)**:四维指标聚合改多数表决/中位数 + 置信标注(项四的聚合侧属指标可信度 P0 主线,项四整体优先级仍为 P1)、Judge 校准与固定验收数据集、来源分析/效果对比在证据链修复后开放。  
> **闸门通过后(第 6 周起):扩展**:新平台接入(项一,闸门=回答成功率/引用可观测率/解析准确率/Judge 一致性达标)、内容实验、新闻稿分发(项三)。  
> **最终阶段:Agent 执行与归因(项五)**:测评→建议→执行→回流闭环 + AI 流量归因。  
> 商务/法务全程并行:信通院可信评测申报、媒体批发网 API 文档与报价、测评自动化条款审查、权威信源小样本验证(人工下单 1～2 篇,第 1～2 周启动)。

## 〇.5 工程通则(适用所有优化项)

1. **灰度与回滚**:所有新能力均通过配置开关 + 白名单灰度发布。代码核查确认 Agent V2 当前没有灰度开关,本次先补建统一灰度机制并作为交付物:环境变量 `AUTOGEO_AGENT_V2_BYPASS_USER_IDS`(白名单,优先级高) > `AUTOGEO_AGENT_V2_ENABLED`(全局开关),后续行动层等试点功能沿用该机制。新增平台用 `GEO_EVALUATION_PLATFORMS_ENABLED`(CSV,默认 `doubao,qianwen,deepseek`)控制启用集,单个平台可独立停用;新闻稿分发用 `PRESS_RELEASE_ENABLED` 开关,首月仅白名单客户。**自动回滚触发条件**:单平台风控触发率连续 2 次超过 30%、测评成功率连续 2 次低于 70%、或 API 通道复校准结果 macro-F1 <0.8 或 Kappa <0.6(与项一校准门槛同指标口径,不另设"一致率"指标;复校准时机默认为平台产品面重大变更或每季度一次,第 0 周一并冻结),即自动停用该平台并通过飞书推送告警;各触发线具体数值(风控/成功率阈值与 macro-F1/Kappa 门槛)在第 0 周基线测量时校准。**观察窗口与生效机制**:指标以自然日为粒度汇总,每日结算一次,"连续 2 次"即连续 2 个测评日不达标;启用集配置由轻量配置表承载(后台修改即时生效,环境变量仅作初始默认值),确保自动停用无需重启服务。
2. **数据迁移通则**:涉及新表(`article_audit`、`publish_channels`、`publish_events` 等)与新增列(`geo_evaluation_records.placement_type` 及项六引用状态字段、runs 的 `campaign_id`、`accounts.api_key_encrypted`)一律 alembic 迁移,**先库后码**;存量行回填默认值(`placement_type='organic'`、`campaign_id=NULL`);每个迁移提供可执行的 downgrade 脚本,发布前在本地库验证 up/down 可逆。
3. **安全红线**:服务商 API Key 仅通过环境变量管理,不纳入代码仓库、不写入日志;生产强制 PostgreSQL,迁移用 `alembic upgrade head`。
4. **测试要求**:每项优化至少包含单元测试(服务层逻辑)、集成测试(API 端到端)、回归测试(发布链路不受影响)三层用例;后端 `ruff + pytest`、前端 `type-check + lint` 纳入 CI,沿用现有 GitHub Actions。
5. **终止标准(质量闸门)**:出现下列情况且相应指标不达标时,终止相关功能上线,不强行推进。证据可观测性不达标时,不发布 QCR(合格引用率)类对外指标;Judge 校准不达标时,来源/引用类指标只展示趋势、不做对外承诺;平台无法稳定采集时,降级为人工采样(Manual),不再追加执行器投入。

## 一、测评平台广度:3 → 7,分批上线(P0)

### 现状与差距

- `backend/services/geo_evaluation_run_service.py:70` 硬编码 `AI_EVALUATION_PLATFORMS = ["doubao", "qianwen", "deepseek"]`,仅覆盖 3 个平台。
- 竞品普遍宣称 20～40+ 平台(泓动 40+、增长超人巧驭 20+、智推 25+);行业分析文章已将元宝/文心/Kimi/夸克列为标准监测对象。
- 测评执行依赖**授权账号 + storage_state 登录态**,经本地 Electron 客户端执行(`_queue_client_evaluation_run` → `local_client_pending`),豆包还有 `browser_verified_login` 二次校验;千问已有独立的限速/重试配置组(`QIANWEN_*` 常量),说明"每平台一个适配组"是既有模式。

### 优化目标

1. 首批新增 **腾讯元宝、百度文心**(微信/百度生态流量大,优先);二批新增 **Kimi、夸克**;合计 7 个。**秘塔暂不纳入(取舍说明)**:竞品调研将其与元宝/Kimi/文心/夸克并列为行业标配监测对象,但其用户规模与商业客户价值低于前四家,列为第三批观察对象,待 7 个平台稳定运行或客户明确提出需求后再行评估,避免首批覆盖范围过宽。**夸克可用性预备案**:夸克以 App 端为主,Web 端 AI 入口的长回答渲染、引用展示与登录态稳定性须在第 0 周探针中验证;若 Web 通道不可用,二批名额由秘塔顶替(秘塔已列为观察对象,顺位前提),不为单一平台引入移动端自动化的高成本投入。
2. 四维指标(可见度/覆盖率/排名/情感)全部支持按 7 平台分平台聚合与对比;引用源(`cited_domains`)作为判卷提取的证据字段同步分平台聚合。
3. 每平台独立限速、风控冷却、账号轮换;注册表化后**新平台接入 = 一条 Spec + 一个执行器**(执行器与选择器维护另计)。**平台覆盖门槛**:不以"注册了 Spec/执行器"作为覆盖定义,每个平台须同时满足**回答成功率、引用可观测率、解析准确率、人工复核一致性**四项门槛才计入覆盖数(门槛数值不取新平台自身基线——新平台无历史数据可测,而以现有 3 平台近 90 天历史表现统计得出:回答成功率与引用可观测率取同期下四分位水平(统计口径:按平台×周聚合 run 成功率与引用可观测率,含失败 run),解析准确率与人工复核一致性参照 Judge 校准同口径,第 0 周从现有平台历史数据算出并冻结,新平台首批满 3 个 run 后复核一次);新平台注册表同时驱动账号校验、执行、限速、报表、前端与测试,消除 `run service`/`analytics`/`Account schema` 等多处平台硬编码。
4. 预留豆包"付费广告位"识别字段(判定逻辑待官方广告系统开放后补充)。


### 解决方案

1. **平台注册表化**:`AI_EVALUATION_PLATFORMS` 改为注册表(`{platform_id: PlatformSpec}`),Spec 含:名称、限速参数组(照 `QIANWEN_MIN_DELAY_SECONDS` 模式)、风控关键词、执行通道(browser/api);`GEO_EVALUATION_PLATFORMS_ENABLED` 控制启用集(运行时以配置表为准、环境变量仅作初始默认值,见工程通则)。
2. **API 通道(有架构前提与校准门槛)**:有官方 API 的平台(DeepSeek、文心)可采用 API 通道测评,降低登录态风控暴露与合规风险;但**当前架构不支持**:Account 模型只有浏览器凭证(cookies/storage_state/user_agent),且 `_resolve_evaluation_account` 对所有平台强制要求 `storage_state` 非空。需先完成三项前置工作:① 复用现有 `Account.auth_mode` 字段承载通道类型(该字段已含 `api=官方API` 枚举值),不新增 `credential_type`,避免两个字段表达同一语义;Account 表新增 `api_key_encrypted` 列做 API key 加密存储(复用 `AUTO_GEO_ENCRYPTION_KEY`,与 Cookie/storage_state 同策略),并制定密钥引用、轮换(新密钥覆盖旧值并留审计日志)、失效、脱敏、审计规则;② 账号解析函数按 auth_mode 分支,并同步修改 `Account.is_authorized` 授权判定(该属性现按 cookies 与 storage_state 判定,API 账号须以 api_key 凭据判定,否则会被误判为未授权);注意 `is_browser_verified` 中 method=api 指验证方式,与 auth_mode=api 指通道类型,二者语义不同,实现时避免混淆;③ Spec 的 `执行通道` 字段。**上线门槛(API/App 表面校准实验)**:校准实验不是独立任务,它以"API 通道最小可用实现"(即上述 Account 扩展)为前提,先用同一批问题(建议 ≥50 条)双通道对比。对比指标不是"两次回答文本是否相同",而是对品牌提及/推荐/引用存在性等标签计算 macro-F1 与 Cohen's Kappa(或置信区间);macro-F1 ≥0.8 且 Kappa ≥0.6 才允许 API 通道进入对外效果口径,否则 API 数据仅作内部趋势参考;该门槛同时作为工程通则"自动回滚"中 API 通道的复校准触发指标,两处口径一致。没有 citation 字段的 API 平台只能用于回答采集,不能用于引用效果承诺。
3. **授权链路**:`frontend/src/core/config/platform.ts:1304` 的 `AI_AUTH_ONLY_PLATFORM_IDS` 增加新平台,复用现有 noVNC 远程授权与本地浏览器桥接授权;浏览器通道平台按豆包标准做 `browser_verified_login` 校验。
4. **测评执行器**:Electron 本地客户端新增各平台会话恢复 + 提问注入 + 回答抓取;选择器独立配置并支持热更新(页面改版时无需重新发布客户端)。
5. **判卷与聚合**:判卷 LLM(`geo_response_judge_service.py`)平台无关,项一范围内无需改动(项二、项六将另行扩展该服务);`geo_evaluation_analytics_service.py` 聚合按 platform 维度展开;`geo_evaluation_records` 增加 `placement_type` 字段(`organic/paid/unknown`,默认 organic,豆包广告位判定待官方开放)。**判卷 prompt 版本化**:第 0 周"判卷 prompt 冻结"是为保证优化前后同口径,而豆包广告系统开放后 `placement_type` 判定必然要改判卷 prompt,届时会破坏历史基线口径。因此判卷 prompt 增加版本号字段,任何改动以新版本号重启基线(旧版本数据按版本号分组对比),不允许静默改动判卷 prompt。
6. **测评成本分层控制(关键补充)**:7 个平台全量且高频运行,将放大账号风控暴露与 LLM 判卷成本(每问题执行次数约为原 3 平台的 2.3 倍)。策略:
   - **平台分层**:核心 3 平台(豆包/DeepSeek/千问)保持现有频率;扩展 4 平台默认低频(如双周)或按需触发;
   - **问题分层**:核心词/品牌词全量测评,长尾问题按 run 抽样(比例可配,建议 30%);
   - **预算上限**:每 run 增加 max_questions × max_platforms 约束,超限自动截断并在报告标注样本量。

### 验收标准

- 首批 2 平台 × 20 问题全链路测评验证通过(授权→提问→判卷→落库→报表);二批同口径。该样本仅作功能验收,不作统计结论。
- 任一平台触发风控时,冷却机制生效且不影响其他平台执行(`_PLATFORM_COOLDOWN_UNTIL` 机制验证)。
- 成本分层生效:长尾抽样与 run 预算上限有单元测试;报告页对抽样/全量有明确标注。
- **CI 模拟执行器**:新增一个模拟平台执行器(本地仿真页面与仿真 API),CI 的端到端测试以它运行全链路,**不消耗真实测评账号**;真实平台仅用于发布前的手工冒烟测试。平台扩容至约 2.3 倍后,若无模拟执行器,CI 资源消耗将不可持续。

### 工作量与风险

- 首批 1.5～2 周(元宝+文心,含授权联调);二批 +1～1.5 周。选择器维护与风控参数调整是主要不确定项,分批上线正是为对冲该风险。

## 二、合规与白帽体系(P0,3·15 合规风险应对)

### 现状与差距

- 2026 年 3·15 晚会曝光"GEO AI 投毒"(虚假测评、虚假排名、批量发布低质内容)行为后,合规成为采购硬门槛;竞品已先行取得权威背书:百分点通过信通院 GEO 可信专项评测、泓动入选信通院首批《GEO 可信承诺》。
- 当前"批量生成 + 15 平台分发"模式存在被归类为低质"灌水"内容的舆论风险;无内容真实性约束、无发布侧审计、无重复度控制;CSDN 行业观察明确"批量内容分发等粗放方式已失效,甚至触发大模型可信性惩罚",AutoGEO 发布端的价值因此受损。
- **代码现状**:生成侧溯源已有相当基础,`SmartArticleBatch` 已记录 4 个 prompt 版本(`question/filter/query_rewrite/article_prompt_version`),`SmartArticleJob` 已记录 `question_id`、检索轮次/命中数、`knowledge_enabled`;发布审批已有用户级日/月配额(自动重置)、可选时间窗口、IP 约束。缺口集中在:发布侧审计(审核记录/发布明细未成链)、跨文章重复度、账号级节流、内容真实性约束。

### 优化目标

1. 任一已发布文章 **5 分钟内可出示完整链路**:选题依据(问题池来源)→ 生成来源(模型/知识库引用,复用现有字段)→ 人工审核记录 → 发布渠道与时间。
2. 内容质量门槛:采用 **64 位 simhash**,新文章与近 90 天同项目文章比对,**汉明距离 ≤3 判为近似重复**并阻断(阈值先按经验值 3 上线,第 0 周基线测量时同步统计项目内距离分布,若分布显示阈值 3 过严或过松,则校准后固化为配置);**"重复率 <10%"的定义 = 近 90 天同项目已发布文章中被判近似重复的占比**;禁止编造数据、评测、排名、用户评价。**两者关系**:"≤3 阻断"是**硬性拦截**,发布后的重复率本应趋近 0;"重复率 <10%"是**复核容忍度**,允许经人工复核通过后的少量近似文章存在,二者是"拦截 + 容忍"而非并列目标。
3. 发布节流:在现有**用户级**配额之上,增加**账号级**日上限与同平台同项目标题去重。
4. 对外输出《AutoGEO 白帽 GEO 方法论》文档,商务口径与"投毒式 GEO"行为明确划清界限。


### 解决方案

1. **内容真实性约束(Prompt 层 + 发布前硬校验)**:文章生成 Prompt 3(正文生成)增加事实性约束段:数据/案例/参数必须来自 RAGFlow 检索结果或明确标注的行业常识,禁止虚构第三方评测、排名、"用户反馈";无知识库支撑的论点降级为定性表述。**发布前硬校验**:在发布审批链增加一道"规则初筛 + LLM 复判"校验,检测正文中无来源支撑的数字/百分比/排名/评测类表述,命中则强制转入人工复核队列(而非直接放行),复核通过后方可发布。实现方式:①规则层以数字/模式抽取列出正文中全部量化表述(数字、百分比、排名、评测结论),无量化表述的文章直接放行,零成本;②命中文章将该表述片段与 RAGFlow 检索留存的证据片段(按 `knowledge_doc_ids` 取回)送 LLM 做对齐判定,仅在命中时触发,单篇成本可控;③判定"无支撑"即转人工复核,规则与 LLM 的误报由人工队列吸收;Prompt 约束是软约束、判卷 `content_risk_flag` 是事后抽检,二者之间必须有这道发布前硬性校验,方可在 3·15 合规背景下向采购方自证。判卷服务(`geo_response_judge_service.py`)增加 `content_risk_flag` 抽检字段,入审计记录。
2. **审计数据表(补齐发布侧,不重复建设)**:新增 `article_audit` 表(模型统一在 `backend/database/models.py`,迁移走 alembic):`article_id`、`question_id`/`batch_id`(直接外链现有 `SmartArticleJob`,不做数据迁移)、`knowledge_doc_ids`(jsonb,新增,现有字段只记数量未记文档ID)、`model_version`(新增)、`reviewer_id/notes`、`simhash`。**发布记录升级为事件链**:`publish_records` 现状为关系表(`PublishRecord`,每篇文章×账号一条终态状态记录,缺中间过程),并非 JSON;本次新增发布事件流(新表 `publish_events`),每条记录事件类型、操作者、时间、内容版本、渠道、供应商订单号、发布 URL、快照哈希、失败/拒审原因、审批依据,与现有终态记录并存(终态表保留、不动现有发布链路),保证幂等、可查询、可审计;并规定租户隔离、RBAC、保留期限、删除与撤回流程。生成/审核/发布三处服务埋点写入。**链路出示交付物**:提供审计链路查询 API 与后台审计详情页(按文章一键展开问题→检索→生成→审核→发布各环节),支持一键导出,作为向采购方出示链路的固定形式;"5 分钟内可出示"以该功能为验收依据。
3. **重复度与节流(含算法契约)**:
   - 生成后计算 simhash 入库,与同项目近 90 天文章比对,距离低于阈值在两处拦截:生成侧阻断入队(任务置失败并提示改写),发布审批侧再次校验拦截(覆盖生成与发布间隔期内新增的近似文章);
   - 发布审批链(`publish_approval_service.py`)在现有用户级配额检查旁增加两条规则:账号级日上限、同平台同项目标题相似去重;沿用其"无配额记录视为无限制(向后兼容)"的兼容策略。
   - **算法契约(含建议默认值,第 0 周用存量数据校准后固化为配置)**:文本归一化采用 jieba 分词、去停用词、全半角与繁简归一,以词特征加权计算 64 位 simhash(标题权重 2 倍);标题相似默认采用字符 3-gram Jaccard 相似度、阈值 0.8,支持对误判申请人工覆盖;跨渠道转载计入重复;重复率分母为近 90 天同项目已发布文章数;事实声明(数据/参数/排名)绑定到证据(知识库文档 ID 或检索结果),避免"≤3 阻断"与"重复率 <10%"在执行时产生争议。
4. **方法论白皮书(商务/文档)**:以"真实品牌资产结构化表达 + 可信信源建设 + 可验证效果"为主线编写,发布于官网与售前材料;强调与 3·15 曝光行为的差异点(真实性溯源、节流、权威信源)。
5. **第三方背书(商务并行,含降级路径)**:申报中国信通院 GEO 服务可信专项评测;关注《GEO 可信承诺》后续批次。**降级路径**:信通院申报存在周期与通过门槛、结果具有不确定性,不阻碍其他优化项推进;若申报未通过或周期过长,则以《白帽 GEO 方法论白皮书》+ 全链路审计日志为主背书,商务口径改用"可验证的真实性溯源"而非"机构背书",不把信通院资质作为 P0 项的唯一依赖。

### 验收标准

- 抽取 10 篇**项二上线后新发布**的文章,全部能从现有批次/任务字段 + `article_audit` 还原"问题→检索→生成→审核→发布"链路。`article_audit` 为新增表,存量已发布文章无 `reviewer_id/notes`/`knowledge_doc_ids`/`simhash` 等字段,仅能还原到"发布记录可溯、审核记录缺失"的降级程度,故验收样本限定为上线后新发文章,不对存量文章承诺完整链路。
- 构造重复选题场景,重复文章被阻断;账号级超发被审批拦截;存量用户未配置新规则时行为保持不变(兼容性用例)。

## 三、权威信源接入:媒体批发网新闻稿分发(P1)

### 现状与差距

- 发布端仅 15+ 自媒体平台,权威新闻媒体分发停在蓝图:`docs/architecture/solutions/08-news-channels.md` 已设计 `PressReleaseService`/`MeijuheziService` 适配器示例/`ContentAdapter`/`PublishChannel` 模型与 API,未实现。
- 竞品已把"权威信源矩阵/信源投喂"作为核心卖点;调研对比数据:权威门户 AI 引用率高 3～5 倍、DA 80～95、百度收录时间即时至 24 小时。3·15 晚会后,低权重自媒体信源的效果进一步弱化,此差距权重上升。

### 优化目标

1. 打通"文章 → 新闻稿适配 → 媒体批发网提交 → 订单轮询 → published_urls 回写 → 进入 GEO 测评引用源"全链路。
2. 分发策略:高价值文章投放付费权威媒体,长尾内容发布至自媒体渠道,受**月度预算约束**。
3. 权威媒体域名在 `cited_domains` 占比的提升先作为待验证假设,不直接写进交付承诺。采用实验组/对照组(或配对)对比方式:选择可比的问题/品牌对,一组投权威媒体、一组不投,记录索引延迟、媒体改稿、发布成本、退款、撤稿与每条增量合格引用的成本,再决定是否把提升目标写入交付口径。


### 解决方案(按既定蓝图六步)

1. **Provider 抽象**:`backend/services/press_release.py` 先落 `PressReleaseProvider` 基类,统一 4 方法签名(`submit_press_release/query_order/get_available_media/estimate_cost`),`MediaWholesaleService` 适配器对照 `MeijuheziService` 示例改 base_url/鉴权 header/字段映射;`PROVIDERS` 注册表 + `smart_distribute()` 按预算选套餐;`PRESS_RELEASE_ENABLED` 开关 + 白名单灰度。
2. **内容适配**:复用蓝图 `ContentAdapter.adapt_for_press_release()`:去除营销 CTA、补充公司全称与联系方式、调整为正式语气、不超过 5000 字。
3. **数据与配置**:alembic 迁移新增 `publish_channels` 表;config 增加 API_KEY/API_URL/`PRESS_RELEASE_MONTHLY_BUDGET`,`.env.example` 同步。
4. **API + 前端**:蓝图既定 5 个端点;前端发布任务增加"新闻稿分发"选项与渠道配置页。
5. **闭环回写与拒审处理**:APScheduler 定时轮询订单状态,`published_urls` 回写文章发布记录并纳入引用源观察清单(清单为已发布 URL 与域名的登记表,仅用于报表层将 `cited_domains` 命中与清单做交集高亮标注,不参与判卷);**拒审/退款流**:订单状态为拒审时自动发起退款跟踪、飞书告警通知、文章回退至自媒体发布队列,并把拒审原因(营销倾向过重、事实存疑等)回写内容适配规则,降低后续拒审率。
6. **前置依赖(商务)**:媒体批发网 API 文档与套餐报价;未到位前先用蓝图示例数据开发适配层与前端。
7. **启动闸门(权威信源引用小样本验证)**:投入全链路开发前,先行开展小样本验证。**验证方式:由商务在媒体批发网后台人工下单 1～2 篇样例稿件**(不依赖系统开发,规避"分发能力尚未建成、却需验证分发结果"的顺序矛盾),稿件发布后,用现有 3 平台对样例内容提问,同时记录两项指标:回答提及率(回答正文提及样例内容或品牌)与引用链接可见率(界面展示可抓取的引用链接),确认权威门户域名确实进入 `cited_domains`、且引用率显著高于自媒体(验证"权威门户 AI 引用率高 3～5 倍"的行业假设)。验证通过后方推进付费套餐与规模化分发;若权威门户未被 AI 引用,则项三目标降级为"百度收录/品牌背书"而非"AI 引用权重",避免全链路验收受制于"链接无法进入 cited_domains"这一外部不可控环节。

### 验收标准

- 1 篇稿件完成 提交→审核→链接生成→链接出现在测评 `cited_domains` 全链路(以小额套餐实测);若引用源小样本验证未通过、项三目标已降级为"百度收录/品牌背书",本项验收相应调整为"提交→审核→链接生成→搜索引擎收录确认",不再以 `cited_domains` 命中为硬性条件。
- 预算约束生效:超月预算提交被拦截(单元测试)。
- 自媒体发布链路回归不受影响。

## 四、效果可验证:优化前→优化后对比与效果交付口径(P1)

### 现状与差距

- 测评已有 `phase` 与 `_verdict` 雏形,但**没有"优化动作 ↔ 效果变化"的关联**:发布批次与测评 run 之间无 campaign 关联,无法回答"这批内容发布后可见度提升了多少"。
- 市场侧,泓动将"效果写入合同"(RaaS)、PureblueAI 将按推荐率验收构建为商业模式;市场已使采购方普遍形成"以效果论验收"的预期。
- **测量方差是行业性盲区**:AI 回答非确定性,同一问题不同 run 结果可能不同;竞品"推荐率 60%"类承诺正是在测量口径上留有操作空间。将测量方法严谨化,既是内部报表可信的基础,也是对外竞争力的差异化优势。

### 优化目标

1. 一键生成项目级"优化前→优化后"对比报告:四维指标变化、引用源结构变化、竞品份额(SOV)变化,**附测量次数与置信说明**。
2. 建立 campaign 关联模型:问题批次 → 文章 → 发布 → 测评 run 可回溯,效果归因到内容动作。
3. 形成对外"效果交付口径"模板,**写明测量方法**(问题集、平台集、测量次数、多数表决规则、周期),支撑按效果商务谈判并避免验收纠纷。


### 解决方案

1. **campaign 关联(含概念边界与归因设计)**:复用现有外键链,测评 run 增加可选 `campaign_id`;创建 run 时支持"绑定最近发布批次",不强耦合。**campaign 语义定义**:一个 campaign = 项目内一次有边界的优化动作周期(如"某批文章发布"或"Agent 执行的一轮优化"),其边界由"绑定的发布批次 SmartArticleBatch + 时间窗"界定;campaign 是聚合/归因的容器,自身不承载生成逻辑,仅把 `SmartArticleBatch`(发布)与 `GeoEvaluationRun`(测评)两个既有实体关联起来,回答"本批动作带来了何种变化"。**归因设计**:campaign 关联只能证明"相关",不能证明"因果提升",还需补齐:① 字段区分:`measurement_type`(baseline/recheck/experiment)、`round_no`(同一 run 内轮次)、`replicate_no`(独立重复)、`retry_count`(失败重试)四个语义不同的字段,不可混用;与现有 `phase`(baseline/ongoing)的关系:phase 保留为执行侧阶段标记,measurement_type 为对比实验语义,两者共存,映射关系写入数据契约;② 基线与复测固定问题集、平台集、模型、地区、账号池、提示词版本(与第 0 周冻结口径一致);③ **对照组(须防内容污染)**:AI 平台检索全网内容,同项目内不投放内容的问题仍会被同一批已发布文章影响;对照优先采用可比品牌配对(同行业未投放内容的问题/品牌对),次选与实验组内容话题覆盖弱相关的同项目问题,并做污染度评估;隔离条件无法满足时,报告只出相关性结论、不宣称因果;④ 样本量、最小可检测效应、置信区间与低样本处理规则预先声明(建议默认:最小可检测效应 5 个百分点,置信区间用 Wilson 95%,单指标有效样本少于 30 时只展示趋势不出结论,第 0 周校准后固化);⑤ 展示边界:报告显式区分"相关性结果"与"因果提升",小样本或未设对照组时只展示相关性、不宣称因果。
2. **重复测量与方差控制(执行侧已存在,缺口在聚合侧)**:代码核查确认 `GeoEvaluationRecord.round_no`(轮次 1/2/3)与 `context_cleaned`(是否清空上下文)字段已存在,且 run service 执行侧**已在按多轮落库**:上下文污染已由 `context_cleaned` 处理。**实际缺口**:① analytics 聚合侧未按 round_no 做多数表决/中位数(当前四维指标按记录平铺计算);② 无翻转率统计。方案改为:聚合层对布尔指标(brand_mentioned/is_recommended 等)按问题×平台做轮次多数表决,连续指标(排名/情感)取中位数,输出翻转率与置信标注;**不动执行侧**。**表决规则**:布尔指标 3 轮取多数(2:1 即胜出);轮次不全(部分平台/部分问题缺轮)时,有效轮数 ≥2 才计入表决、且报告中显式标注有效轮数与缺失轮,单轮结果仅作参考不计入对外口径;平局处理:有效 2 轮且结果 1:1 相反时判为"不稳定",该问题×平台当次不计入对外口径、仅计入翻转率统计并在报告标注。**数值下限**:翻转率分母(两次 run 均有有效判定的问题×平台对)少于 30 对时不出翻转率,仅展示原始轮次一致率并标注样本量。**翻转率定义**:同一问题×平台在相邻两次 run 之间布尔判定发生翻转(如 未提及↔提及)的比例,判定取各 run 多数表决后的结果(判为"不稳定"的问题×平台对不参与),分母为两次 run 均有有效判定的问题×平台对;翻转率作为测量稳定性披露项,不作效果承诺分子。③ 补账号侧防污染:同一账号长期高频提问同一品牌仍可能被平台个性化,增加**测评账号与发布账号强制隔离**(账号分组已有 `group_id`/`tags` 字段可承载)、重复测量轮换同平台多账号(多账号选择逻辑已存在)、账号健康度(`health_score` 字段已有)纳入测评可用性判断。
3. **对比报告服务**:`geo_evaluation_analytics_service` 新增 `get_campaign_impact(project_id, campaign_id)`,做基线测评与优化后测评的对比,输出四维指标变化、`_verdict` 结论、`cited_domains` 结构变化、`matched_names` 提及率与份额变化 + 置信标注。
4. **API + 前端**:`/api/geo-evaluation/projects/{id}/campaign-impact`;报告页"效果对比"标签页(双时段对比 + 归因列表),复用 `GeoFiveMetrics.vue` 数据模式。
5. **效果口径模板**:售前/交付文档明确三项内容:测量对象(固定问题集/平台集)、测量方式(N 次多数表决)、计算方法(指标公式与样本规则),并作为合同附件。**平台集冻结规则**:平台是分批上线的(3→5→7),基线与复测必须用同一平台集对比,否则"平台数 3→7 的天然增益"会混入"可见度提升"造成归因失真;平台扩容带来的增量单列标注(平台数 N→M 的扩展增益),不允许把"多测了几个平台"算进"优化动作带来的提升"。**抽样统计功效**:长尾问题按 run 抽样(默认 30%)会缩小样本量,进而影响 `cited_domains` 占比与翻转率的统计显著性;口径模板需写明"抽样比例对统计功效的影响",权威信源验证阶段(优化项三闸门)保留全量样本,不抽样。

### 验收标准

- 指定项目一键输出含置信标注的 3 个月效果报告。
- 任一提升指标可下钻到发布批次与文章。
- 同一 run 重复测量数据落库且翻转率在报表可见(证明方差控制切实生效)。

## 五、Agent 行动层:从引导到执行(P2)

### 现状与差距

- `backend/services/agent_v2/`(LangGraph)当前定位是新手引导 + 工具裁剪 + 三道护栏,生成与发布执行依赖用户手动操作。
- 国际方向已明确"行动层"是下一发展阶段:Profound Agents 自动生成 AI 优化内容并执行营销工作流;国内头部厂商亦在强化"全链路自动化"的产品定位。

### 优化目标

1. Agent 能读取测评短板 → 给出结构化优化建议 → **人工确认后自动执行**(补问题、重生成、调整信源),形成"测评→建议→执行→回流测评"闭环。
2. 复用现有 `confirm` 节点与三道防线护栏,**所有执行类动作必须过人工确认**,不开放自主发布。
3. 建议命中率可度量:建议被采纳执行后,下一轮测评对应问题可见度提升率入报表。


### 解决方案

1. **新增只读诊断工具**(挂载机制说明:当前不存在 `get_tools_for_state()`,真实机制是 `agent_node.py` 的 `_TASK_TYPE_TOOLS` 按任务类型裁剪 + `tools/VALID_TOOLS` 注册,且 `tools_node.py` 注释明示两处清单需保持一致,新增工具必须同时改两份清单,漏一处会静默失效):`get_visibility_gaps(project_id)`,聚合可见度低/未被推荐/我方无引用的问题清单与原因分类(内容缺失/信源弱/情感负)。
2. **新增建议工具**:`propose_optimization_plan(project_id)`,基于 gaps 生成动作清单(新增问题 N 条→生成文章→建议渠道:权威媒体或自媒体),输出结构化 JSON 供前端渲染确认卡。
3. **执行编排**:确认后按清单复用现有服务层能力(问题池生成、文章生成、发布审批链),**不新写执行引擎**,仅做编排;执行进度经 SSE 推送(已有流式通道)。
4. **护栏沿用 + 工程约定(含合规一致性)**:执行类工具全部注册为需 `confirm`;`guardrail` 掩码清单同步更新;发布仍遵循既有审批约束,Agent 不能绕过配额/时间窗口/IP 规则。**合规闸门统一生效**:Agent 编排触发的"补问题/重生成/调整信源"与人工触发经过完全相同的链路,simhash 重复度阻断、内容真实性发布前硬校验、账号级节流对所有入口(手动/Agent/批量)统一生效,Agent 不因编排路径而绕过新增合规闸门。**必须遵守两条既有工程约定**:① 改引导话术要同步修改 `agent_node.py` 的 SYSTEM_PROMPT 与工具 reply(只改一处会被 LLM 第二轮改写覆盖);② 新工具接入不能破坏 6 步新手引导状态机的顺序约束(绑定账号必须等文章生成完成等),新工具按会话状态动态裁剪。**操作治理**:人工确认仅为第一层保障,还需建立权限校验、确认过期(确认后超时需重新确认)、操作预览(执行前展示将产生的影响)、幂等键(同一动作不重复执行)、部分失败处理、取消与重试、预算/配额限制、执行审计日志;**试点最小集**:权限校验、幂等键、执行审计三项随白名单试点先行,其余(确认过期、操作预览、部分失败处理、取消与重试、预算/配额)随灰度扩面分批补齐;并对 Agent 可能读取的外部网页内容做 Prompt Injection 防护(检索结果/引用页内容不直接进入系统提示词)。
5. **灰度**:使用工程通则补建的 Agent V2 灰度机制(白名单 `AUTOGEO_AGENT_V2_BYPASS_USER_IDS` > 全局开关 `AUTOGEO_AGENT_V2_ENABLED`),行动层工具先在白名单范围内试点,再逐步扩大范围。
6. **效果回流**:执行完成的动作自动打 campaign 标记(与优化项四打通),下轮测评自动关联。

### 验收标准

- 演示完整闭环:测评发现"某类问题品牌未覆盖"→ Agent 建议 5 条 → 用户确认 → 自动生成并提交审批 → 下轮测评该类问题可见度提升可量化。
- 全程护栏验证:未确认的执行动作 100% 被拦截;新手引导 6 步顺序回归用例通过。

## 六、竞品与来源分析(证据链修复 P0 + 聚合 P2)

### 现状与差距(基于代码静态核对)

- **数据链路断裂,来源分析数据"算得出来但不可信"**:`GeoCompetitorAnalysis.vue` 前端组件、`GET /clients/{client_id}/competitor-analysis` 端点、analytics 的 `get_client_competitor_analysis` 虽已存在,但**上游证据链断裂**:测评 Worker 提交结果时 `citations` 固定为 `[]`(`backend/workers/geo_evaluation_worker.py`),AI 平台回答自带的引用链接被丢弃,`cited_domains` 只能由判卷环节从纯文本推测,真实新测评可能没有任何引用数据。
- **`share` 口径错误**:当前 `share = 提及次数 / 有效回答数`,多品牌同时出现时总和可 >100%,不是真正的"份额"(SOV);域名同理是"引用次数/回答数"而非"引用份额"。且仅有一处简单的全称/简称互包含归一化(`_normalize_brand_text`),无品牌别名表、系统性实体归一化、来源质量分级、多轮去重。
- **有利现状**:记录表已预留引用相关字段(`raw_citations`/`cited_urls`/`cited_domains`/`citation_supported`/`own_source_cited`),并有 `capture_method` 采集方式标记;证据链修复主要是执行链路打通(客户端抽取、Worker 传递、状态区分),表结构大部分现成,仅需新增引用状态字段。
- 其余差距:① **项目级聚合**(当前仅客户级);② `/api/reports/*` 报表未接入竞品维度;③ 无 SOV 时间趋势。

### 优化目标

1. 先修引用证据链:citations 真实落库、状态区分、回答-引用关联,使 `cited_domains`/`matched_names` 可信。
2. 份额口径重写为 `mention_rate`(提及率)/`answer_share`(回答份额)/`citation_share`(引用份额)/`qualified_citation_share`(合格引用份额),并补品牌别名/实体归一化/来源质量/多轮去重。
3. 项目级竞品榜 + 引用域名 TOP N + SOV 趋势线纳入数据报表体系。

### 解决方案

1. **引用证据链修复(前置,P0)**:测评 Worker 不再丢弃引用,采集 AI 平台回答自带的 citations 并真实落库。**实现层与工作量归属**:引用链接必须在 Electron 客户端执行器内抽取(优先监听网络响应层,DOM 提取兜底,抽取规则按平台 Spec 配置),后端只承接状态区分、关联与脱敏;该项属客户端改造,客户端工作量在原约 2 人周基础上相应上调(首批两平台估计另加 0.5～1 人周,第 0 周复核)。新增引用状态字段并区分三态(平台无引用能力记 null,抓取成功但零条记空列表,抓取异常记 unavailable,判定映射表随平台 Spec 配置)、原始证据(引用链接+快照)保存、回答-引用关联、幂等与脱敏;涉及 `geo_evaluation_worker.py`、`geo_response_judge_service.py`、`geo_evaluation_records` 表结构与迁移。
2. **份额口径重写(前置,P0)**:聚合层把 `share` 拆为四个指标:`mention_rate`(品牌被提及的回答占比,可 >100% 因多品牌同现)、`answer_share`(各品牌提及数/总提及数,总和=100%)、`citation_share`(各域名被引用数/总引用数)、`qualified_citation_share`(仅计入有原始证据、来源质量合格的引用);补品牌别名表、系统性实体归一化(在现有 `_normalize_brand_text` 基础上升级为别名表驱动)、多轮去重。**口径版本化**:与判卷 prompt 同规则,指标口径任何改动以新版本号生效;旧 `share` 字段只读保留、停止更新,新指标自切换日起算;跨版本的历史对比在报告显式标注口径版本,不允许静默改口径。
3. `get_client_competitor_analysis` 参数化复用出项目级版本,端点 `/projects/{project_id}/competitor-analysis`。
4. `/api/reports/overview|stats` 增加竞品维度汇总字段(竞品提及 TOP5、我方信源引用占比)。
5. 前端测评详情页"竞品与来源分析"标签页增加 SOV 趋势线(按 run 时间序列展开)。
6. **报表性能**:平台扩展至 7 个 + 多轮测量后 `geo_evaluation_records` 数据量级约为当前的 2.3～3 倍,竞品榜/SOV 趋势/效果对比都是全表聚合。补充措施:复合索引 `(client_id, project_id, platform, asked_at)`(现仅有 platform 单列索引)+ 周级预汇总表(由 APScheduler 定时生成,粒度分两档:问题×平台×run 粒度支撑多数表决与翻转率回溯,平台×日粒度支撑趋势图),聚合页读汇总表、明细页读原表。

### 验收标准

- 引用证据链:一条真实测评的 citations 非空且与回答关联可回溯;`null/[]/unavailable` 状态在报表正确区分。
- 份额口径:四指标单元测试通过;多品牌同现时 `answer_share` 总和=100%、`mention_rate` 可 >100%;补品牌别名/实体归一化/多轮去重的专用单元、API、前端端到端测试。
- 三个聚合点(项目级、报表维度、SOV 趋势)各一条冒烟用例(测试数据构造脚本 `seed_competitor_analysis.sql` 可复用;该脚本现位于仓库外的工作区根目录,应移入仓库 `scripts/` 统一管理)。
